# Add content to the course

You are helping an instructor add content to a PrairieLearn course that teaches beginners competitive programming in Python. The instructor wants to move **fast** but stay **in control**. So you draft everything, and they approve or adjust it at each step, usually with one click.

The course root is the directory containing `infoCourse.json`; it's the repo this skill lives in. Run every command from there. `tools/` holds deterministic helpers. Use them rather than re-deriving their logic, because they encode lessons already learned (e.g. how sample outputs are generated, what PrairieLearn rejects on sync).

## How to interact

- **Ask at every decision point, with the AskUserQuestion tool.** Put your best draft first, labeled "(Recommended)", so accepting it is one click. Show draft content (problem statements, test plans, JSON settings) in the option's `preview` field: the question dialog is often the only thing the instructor sees. They can type changes via "Other" or the notes field.
- Batch related decisions into one AskUserQuestion call (up to 4 questions) instead of asking one at a time. Don't ask things the tools can answer, such as the next free number, existing topics, or which questions already exist.
- Write a question's files only after the instructor approves its spec. Outputs generated by the tools (expected outputs, the samples block, UUIDs) need no approval.
- If the instructor's message already answers a question (e.g. "make HW2 with these 3 problems: ..."), don't ask it again. Just reflect it in the next confirmation.

## Step 0 — Orient (no questions yet)

```bash
python tools/course_index.py      # question bank, assessments, next free numbers
git status --short                # uncommitted changes?
```

Read `infoCourse.json` for the topics and tags. If `git status` shows changes you didn't make, they are most likely the instructor's own manual edits. Never overwrite or revert them. Build on top of them, and leave them out of your commit unless the instructor says otherwise (mention them at the end). Read edited `question.html` files closely: they show how the instructor likes things written, and the style guide below came from exactly such edits.

## Step 1 — What are we doing?

Unless the request already makes it clear, ask which task this is:

1. **New assessment** (homework, quiz, or exam): steps 2–7
2. **Add questions to an existing assessment**: pick the assessment, then steps 3–7
3. **Add questions to the bank only** (on no assessment yet): steps 3, 4, 6, 7
4. **Edit an existing question**: see "Editing an existing question" below

## Step 2 — Assessment settings

Read `references/assessments.md`. It has the presets, the JSON for each, and the list of questions to ask for exams.

- Ask for the set (Homework / Quiz / Exam) and the title. Propose the label from `course_index.py` (e.g. "HW1", "Q2").
- **Homework** and **Quiz** have presets. Show the preset in a preview and ask the instructor to confirm or change it. For homework, always ask the due date.
- **Exam** has no preset, by the instructor's choice. Ask every item on the exam checklist.
- When adding to an existing **Exam-type** assessment (quizzes are Exam-type too), warn the instructor first. Students who have already started it won't see the new questions, because Exam instances are fixed when created.

## Step 3 — Question list

1. If the instructor hasn't listed the questions yet, ask for one-line ideas. Their style looks like "t3 - find sum of all even numbers (not even indices!)".
2. **Offer reuse.** If the bank has questions on the same topic that this assessment doesn't use, offer them in a multi-select. Skip this when the bank has nothing relevant.
3. For the new ideas, propose a plan table: one row per question with folder/ID, title, format, topic, and tags. Present it in a preview and get it approved. Formats:
   - **stdio workspace**: a full VS Code workspace with the judge. This is the default for coding problems.
   - **stdio editor**: an in-page code editor with the same judge. Use it for short exercises, where opening a workspace is overkill.
   - **non-code**: `pl-multiple-choice`, `pl-checkbox`, `pl-integer-input`, `pl-string-input` or `pl-order-blocks`. Use it for concept checks like "what does this loop print?".
   Use existing topics and tags. If an idea needs a new topic or tag, propose adding it to `infoCourse.json` as part of this approval.

## Step 4 — Draft each question, then build it

Go question by question, in order. For coding questions read `references/stdio-questions.md`. For non-code questions read `references/non-code-questions.md`.

**4a. Spec.** Draft the statement, the input/output format with constraints, 1–2 samples with one-line explanations, and the starter code. Show it in a preview. Offer options such as "Approve (Recommended)", "Simpler", and "Harder"; the instructor's notes can carry anything else.

**4b. Test plan** (coding questions). List the hidden tests by intent, e.g. "n = 0 (edge), all odd values → 0, negatives, N = 1000 random". About 6–10 tests in total, including the samples, is right for beginner problems. Get approval. You can combine 4a and 4b into one AskUserQuestion call (two questions) to save a round trip.

**4c. Build.** Get a new UUID for each question, quiz or exam from `python -c "import uuid; print(uuid.uuid4())"`. Never copy a UUID from another file. Write the files from the templates, then let the tools generate everything else:

```bash
python tools/check_question.py questions/<topic-folder>/<slug> --fix
```

`--fix` runs `tests/solution.py` on every case to write the expected outputs. It also regenerates the samples block in `question.html` from the visible cases. So never hand-type expected outputs or sample outputs; the tool keeps the statement, samples and tests consistent.

## Step 5 — Assemble the assessment and review it

Write or update `infoAssessment.json` (see `references/assessments.md`). Then show one final summary in a preview and ask for a last approval: label, title, type, access settings, and each question with its points. This is the instructor's chance to reorder questions or change points before verification.

## Step 6 — Verify (always run everything)

```bash
python tools/validate_course.py                # schema + cross-reference checks, whole course
python tools/check_question.py --all           # every solution matches its tests, samples in sync
python tools/test_judge.py <each new/changed judge question dir>   # real grader image in Docker
```

- `validate_course.py` needs `jsonschema` (`python -m pip install jsonschema` if it warns).
- `test_judge.py` needs Docker. If it exits with code 2, start Docker Desktop: on Windows run `Start-Process "$env:LOCALAPPDATA\Programs\DockerDesktop\Docker Desktop.exe"`, or `C:\Program Files\Docker\Docker\Docker Desktop.exe` for system installs. Wait until `docker info` succeeds, then re-run. The first run pulls `prairielearn/grader-python`, which takes a few minutes.
- For non-code "what does this print" questions, run the snippet with Python and confirm the output matches the `correct-answer`.

Fix every error and re-run until it's clean. Warnings deserve a look too. Report success only after you've seen passing output; if something can't be made to pass, say so plainly.

## Step 7 — Commit and report

Commit automatically, locally only, and never push. Stage only the paths this run created or changed: `git add <paths>`, not `git add -A`, so the instructor's unrelated edits stay out of the commit. Write a descriptive message, e.g. `Add HW2: List operations (3 new questions)`. End it with the attribution trailer your session instructions specify, if any.

Then give a short report:
- what was created (label, title, question IDs) and the key settings
- the verification results in one line each
- how to see the content: in a running local PrairieLearn, click **Load from disk**; otherwise run `bash start-local.sh` from WSL and open <http://localhost:3000/pl>. Instructors can preview questions without the assessment being open, because staff always have access.
- any uncommitted changes of the instructor's that you left alone

## Editing an existing question

1. Show the question's current statement summary, test count and where it's used (from `course_index.py`), and ask what to change.
2. Make the change, keeping the `uuid` and the folder name. The UUID ties the question to its student data and statistics. The folder path is the question ID that assessments reference, so renaming it breaks them.
3. If you change tests or expected behavior on a question that students have already submitted to, tell the instructor. Old submissions keep their old scores unless the instructor regrades them in PrairieLearn (assessment → Regrading).
4. Re-run step 6 for that question, then commit as in step 7.

## Style guide (from the instructor's own edits)

- **`question.html` contains only:** the statement, **Input:**, **Output:**, the generated samples block, and the workspace or editor element, followed by the submission panel. Don't add "how to write/test/submit your code" paragraphs. The assessment's intro text already covers that, and the instructor removed such boilerplate from every Q1 question.
- **Wording:** say "indices", not "positions". Keep statements short and precise, and don't over-explain things these students already know from class. For example, the instructor deleted "Indices start at 0, as in Python."
- **Difficulty:** the students are beginners. The intended solution should be short and use only constructs from the topic at hand (loops, `range()`, `if`, lists, …). Keep constraints small (N ≤ 1000) so that no efficiency tricks are needed.
- **Input format:** follow what the course already does. A count `N` comes first, then one value per line. Two lists appear as `N`, then the N values of `a`, then the N values of `b`. Single values go one per line. Output is one value per line.
- **Starter code:** a comment header that restates the task in one or two lines and gives the test command. Pre-write the `input()` lines for single values, but leave building lists to the student, since that is part of what they're practicing.
- Question folders go under the topic: `loops-and-lists/`, `list-operations/`, `string-operations/`, `functions/`, `dicts-and-sets/`, `standard-library/`. Use lowercase-hyphenated slugs.

## Gotchas that break things

- **Homework** `autoPoints` must be a single number, and **Exam** `autoPoints` lists must be non-increasing. Time limits work only on **Exam**-type assessments.
- Workspace questions need `"singleVariant": true`, and their `gradedFiles` must include the judge's `studentFile` (`main.py`).
- `question.html` is parsed as HTML and rendered with Mustache. Escape `<`, `>` and `&` in text and code; better yet, load code from a file with `<pl-code source-file-name=...>`. Avoid literal `{{` unless `server.py` provides it.
- Dates in JSON are local course time (America/Vancouver) with no UTC offset, e.g. `"2026-11-20T23:59:59"`. For "open now", use today at `T00:00:01`.
- Keep LF line endings. `.gitattributes` enforces them in git, and the tools write LF.
- An assessment with no `accessControl` is invisible to students. That's fine for drafts, but say so in the report.
